# GLI Claude Design AI 작업지시서

버전: 2026-08-12
대상 브랜치: `design/claude-ui-refresh`
디자인 기준 원본: `design-handoff/source/gli-demo.dc.html`
작성 역할: Codex PM / 백엔드·통합 개발
수행 역할: Claude Design AI / UI·UX 시안 제작

## 1. 작업 목적

현재 승인된 GLI 디자인을 유지하면서 다음 사항을 보완한다.

1. 랜딩 페이지에서 GLI의 핵심 기능이 **AI 투자 탐색**임을 즉시 이해하게 한다.
2. 랜딩 페이지와 실제 자산 탐색 페이지의 역할을 명확히 분리한다.
3. 검색 중 현재 진행 단계를 사용자가 이해할 수 있게 한다.
4. 모바일에서 글자, CTA, 검색, 탐색 결과와 메뉴의 가독성을 높인다.
5. 자동 이동 콘텐츠의 접근성을 개선한다.
6. 확정된 오타와 데모 고지 정책을 반영한다.

이번 작업은 새로운 브랜드 디자인을 만드는 일이 아니다. 기존 Claude 최종안의 폰트, 색상, 카드 형태, 라운드 값, 그림자, 아이콘 스타일과 정보 위계를 그대로 사용한 **제한적 UI 개선 작업**이다.

## 2. 역할과 책임

### Claude Design AI

- HTML/CSS/시안용 JS를 사용해 최종 시각안을 만든다.
- PC와 모바일에서 직접 보이는 결과를 책임진다.
- 이 문서에 명시된 범위 밖의 카피, 데이터, 가격, 정책, 메뉴를 임의로 변경하지 않는다.
- 변경이 필요하지만 이 문서에 승인되지 않은 사항은 구현하지 말고 별도 제안 목록으로 남긴다.

### Codex

- PM이자 백엔드·통합 개발자다.
- Claude가 확정한 HTML을 React 구조로 옮기고, API·라우팅·상태·이벤트를 연결한다.
- Claude의 시각 코드를 자의적으로 재설계하지 않는다.
- 백엔드 상태와 맞지 않는 표현이나 구현 불가능한 동작이 있으면 적용 전 사용자에게 보고한다.

## 3. 절대 유지 사항

다음은 이번 작업에서 변경하지 않는다.

- Pretendard / Schibsted Grotesk 사용 원칙
- 현재 forest green, green, lime, gold, paper, surface 컬러 체계
- 현재 카드 반경, 그림자, 선 두께와 기본 컴포넌트 스타일
- GLI 로고와 헤더·푸터의 전체 브랜드 구조
- 회사 정보, 경영진 정보, 자산 데이터, Trust Score, 멤버십 가격과 권한
- 랜딩 이외 페이지의 전체 정보 구조
- 랜딩 기본 헤드라인
  - `국가와 자산의 경계를 넘어,`
  - `검증된 투자 기회를 탐색하세요`
- 자산 탐색 페이지가 실제 AI 검색과 결과 표시를 전담한다는 구조

## 4. 핵심 정보 구조 원칙

### 랜딩 페이지의 역할

랜딩은 GLI의 가치, 작동 원리, 검증 신뢰와 서비스 범위를 설득하는 **마케팅·진입 페이지**다.

랜딩에는 다음 기능을 넣지 않는다.

- 실제 AI 검색 입력창
- 검색 필터
- 실제 검색 실행과 진행 상태
- 검색 결과 목록
- 탐색 페이지와 동일한 대화창
- 탐색 페이지와 동일한 자산 그리드

랜딩에서 보여줄 것은 다음 네 가지다.

1. GLI가 AI로 투자 기회를 찾는 서비스라는 점
2. AI 탐색과 사람의 검증이 결합된다는 점
3. 실제로 다루는 국가·자산과 검증 결과의 짧은 증거
4. 실제 자산 탐색 페이지로 이동하는 명확한 CTA

### 자산 탐색 페이지의 역할

`/explore`만 다음 기능을 제공한다.

- 자연어 질문 입력
- 예시 질문 선택
- 후속 대화와 조건 보완
- AI 검색 단계 표시
- 국가·거래 유형·자산 분류 필터
- 결과 개수, 정렬, 카드 목록
- 결과 없음과 검색 범위 확대 질문
- 이전 검색 상태 복원

## 5. 랜딩 페이지 수정 지시

### 5.1 히어로의 핵심 CTA

현재의 작은 `투자 기회 탐색하기` 버튼은 GLI의 핵심 기능에 비해 시각적 우선순위가 낮다.

다음 기준으로 CTA를 재설계한다.

- 문구: **`GLI AI와 투자 탐색 시작`**
- 기존 lime 계열 기본 CTA 스타일을 사용한다.
- 데스크톱에서 다른 보조 버튼보다 폭, 높이, 대비가 명확히 커야 한다.
- 권장 최소 높이: 56px
- Sparkles 또는 Search 계열 Lucide 아이콘을 사용한다.
- CTA 아래에 짧은 보조 문구를 둔다.
  - **`예산·국가·목적을 대화로 입력하면 AI가 조건을 정리합니다.`**
- 보조 CTA `GLI 검증 방식`은 유지하되 시각적 위계를 낮춘다.
- CTA 이벤트 훅은 기존 `goHome`을 유지한다. Codex가 `/explore` 라우팅과 연결한다.

### 5.2 실제 검색창은 추가하지 않음

랜딩 히어로에는 입력 가능한 textarea, 검색 버튼, 필터를 추가하지 않는다. 실제 질문은 자산 탐색 페이지에서만 입력한다.

AI 기능을 설명하기 위한 질문 예시는 `INSIDE GLI`의 UI 모형 한 곳에서만 유지한다. 동일한 질문 예시 UI를 히어로와 다른 섹션에 반복하지 않는다.

### 5.3 대표 자산 카드

히어로 우측의 대표 검증 자산 카드는 AI 결과의 구체성을 증명하는 요소로 유지한다.

- 검색 결과 그리드처럼 보이지 않게 단일 카드만 사용한다.
- 카드에 필터, 정렬, 페이지 이동을 추가하지 않는다.
- Trust Score와 검증 단계가 핵심 증거로 보이게 한다.
- CTA보다 먼저 시선을 빼앗지 않도록 시각적 대비를 조정할 수 있다.

### 5.4 랜딩의 자산 노출

FEATURED 자산은 최대 3건의 편집형 미리보기로만 유지한다.

- 탐색 페이지의 전체 카드 목록과 동일한 화면처럼 보이지 않게 한다.
- 필터, 결과 건수, 정렬, 리스트 전환을 넣지 않는다.
- 섹션 끝의 CTA는 `GLI AI와 전체 자산 탐색`으로 통일할 수 있다.
- 같은 자산 목록이나 같은 검색 UI를 다른 랜딩 섹션에서 다시 반복하지 않는다.

### 5.5 랜딩 첫 화면의 모바일 순서

모바일에서는 다음 순서를 사용한다.

1. Kicker
2. H1
3. 리드 문구
4. 핵심 CTA
5. CTA 보조 문구
6. 보조 CTA
7. 축약 통계
8. 대표 자산 카드

핵심 CTA가 첫 화면 안에서 보이거나, 최소한 스크롤 없이 일부가 보여야 한다.

## 6. 자산 탐색 페이지 수정 지시

### 6.1 검색 진행 상태

현재 네 단계가 동일하게 보이는 구조를 실제 상태가 구분되도록 개선한다.

단계:

1. 요청 이해
2. 후보 탐색
3. 근거 검토
4. 답변 구성

상태 표현:

- 대기: 중립적인 line / ink-2 계열
- 진행 중: green 또는 lime 강조, 가벼운 진행 애니메이션
- 완료: 체크 아이콘과 완료 색상
- 오류: red 계열, 단계명 옆에 짧은 오류 안내
- 결과 완료 후 네 단계가 모두 완료 상태로 남아야 한다.

가짜 진행률 퍼센트는 사용하지 않는다.

Claude 시안에는 다음 상태가 모두 확인 가능해야 한다.

- idle
- understanding
- searching
- reviewing
- composing
- complete
- error

권장 클래스 계약:

```text
.pipe-step.is-idle
.pipe-step.is-active
.pipe-step.is-done
.pipe-step.is-error
```

Codex가 검색 API 상태에 맞춰 클래스를 연결할 예정이다.

### 6.2 모바일 진행 상태

모바일에서는 네 단계를 한 줄에 억지로 모두 표시하지 않는다.

- 기본 표현: `2/4 후보 탐색 중`
- 현재 단계와 다음 단계만 보이게 하거나, 가로 스크롤 없이 압축한다.
- 상세 설명은 한 줄 또는 최대 두 줄로 제한한다.
- 검색 중 사용자가 무엇을 기다리는지 명확히 보여준다.

### 6.3 모바일 검색 입력

- textarea와 탐색 버튼을 세로로 배치한다.
- 탐색 버튼 폭: 100%
- 버튼 높이: 52~56px
- 입력 글자: 최소 16px. 모바일 브라우저의 자동 확대를 방지한다.
- Enter/검색 키 실행이 가능함을 고려하되 화면에 키보드 설명 문구는 넣지 않는다.
- 입력창은 지나치게 높지 않게 시작하고 내용에 따라 확장되게 설계할 수 있다.

### 6.4 예시 질문

- 데스크톱에서는 현재 칩 형태를 유지한다.
- 모바일에서는 세 개를 모두 세로로 쌓지 않는다.
- 한 줄 가로 스크롤 + scroll snap을 사용한다.
- 다음 칩의 일부가 보여 스크롤 가능성을 알 수 있게 한다.
- 터치 영역은 최소 48px 높이를 유지한다.

## 7. 모바일 공통 UX 지시

### 7.1 기본 가독성

- 일반 본문과 인터랙션 텍스트는 최소 14px을 유지한다.
- 입력 글자는 최소 16px을 유지한다.
- 12~13px은 푸터 법적 고지, 모형 UI의 장식 레이블 등 제한적인 영역만 허용한다.
- 한글은 `word-break: keep-all`을 유지한다.
- 모바일 H1은 고정 `<br>` 때문에 어색해지지 않도록 breakpoint에서 자동 줄바꿈을 허용한다.
- 360px, 390px, 430px에서 가로 넘침이 없어야 한다.

### 7.2 모바일 헤더

헤더는 다음 우선순위로 단순화한다.

1. GLI 로고
2. AI 탐색 진입 버튼 또는 아이콘+텍스트
3. 메뉴 버튼

로그인, 관심자산, 소개, 멤버십 등은 모바일 메뉴 안에서 접근 가능해야 한다. AI 탐색 진입은 메뉴 안에만 숨기지 않는다.

모바일 AI 탐색 버튼은 기존 CTA 색상 체계를 사용하되 로고나 메뉴보다 과도하게 크지 않게 한다.

### 7.3 랜딩 통계

현재 520px 이하에서 통계 3개가 세로 한 열로 바뀌어 첫 화면이 길어진다.

- 모바일에서도 3열 축약형 또는 2+1의 조밀한 형태를 우선 검토한다.
- 숫자와 짧은 레이블만 표시한다.
- 카드 높이와 숫자 기준선을 일치시킨다.

### 7.4 자산 카드

모바일 카드 정보 우선순위:

1. 사진과 GLI 검증/추천·거래 유형
2. 국가·도시
3. 자산명
4. 원 가격과 환산 가격
5. Trust Score
6. 면적·침실·욕실 또는 프로젝트 핵심 항목

- 제목과 가격을 absolute positioning으로 배치하지 않는다.
- 긴 자산명과 가격 범위가 서로 겹치지 않아야 한다.
- 카드 전체는 상세 이동 영역으로 유지한다.
- 관심자산 버튼은 카드 이동 이벤트와 충돌하지 않는 별도 터치 영역으로 둔다.

### 7.5 자산 상세

- 5단계 정보 탭은 가로 스크롤과 scroll snap을 사용한다.
- 선택된 탭이 가능한 한 중앙에 오게 한다.
- 오른쪽 끝에 약한 fade 또는 잘린 다음 탭을 보여 추가 탭이 있음을 알린다.
- 주요 행동의 우선순위는 `전문가 상담` > `관심자산` > `탐색 결과로 돌아가기`다.
- `탐색 결과로 돌아가기`는 상단과 본문 하단에 제공하되 모바일 고정 행동 영역에는 넣지 않는다.
- 하단 고정 행동 영역을 제안할 경우 본문과 푸터를 가리지 않도록 safe-area를 적용한다.

### 7.6 모바일 메뉴

- 메뉴 높이가 화면을 넘으면 내부 스크롤이 가능해야 한다.
- 열린 상태에서 배경과 메뉴의 경계가 명확해야 한다.
- 바깥 영역을 누르거나 메뉴 항목을 선택하면 닫힌다.
- Esc와 키보드 포커스 순서를 고려한다.

## 8. 움직임과 접근성

### 8.1 자동 이동 콘텐츠

Trust 자산 ticker와 후기 marquee에 모두 적용한다.

- hover 시 일시정지
- keyboard focus가 내부에 있을 때 일시정지
- touch interaction 후 일정 시간 일시정지
- `prefers-reduced-motion: reduce`에서는 자동 이동 중지
- 콘텐츠를 읽을 수 없는 속도로 이동시키지 않는다.

권장 CSS 계약:

```css
.tick:hover .tick-in,
.tick:focus-within .tick-in,
.vmarquee:hover .vtrack,
.vmarquee:focus-within .vtrack {
  animation-play-state: paused;
}

@media (prefers-reduced-motion: reduce) {
  .tick-in,
  .vtrack {
    animation: none;
    transform: none;
  }
}
```

필요하다면 작은 일시정지 아이콘을 제안할 수 있으나, 새 버튼을 실제 시안에 추가하기 전 별도 제안으로 보고한다.

### 8.2 포커스와 터치

- 모든 링크·버튼에 명확한 focus-visible 상태를 둔다.
- 일반 터치 영역은 최소 48×48px을 유지한다.
- 아이콘 전용 버튼에는 `aria-label`을 둔다.
- 색상만으로 검색 단계나 등급 상태를 구분하지 않는다.

## 9. 확정 문구 수정

### 9.1 오타

디자인 원본 전체에서 다음 오타를 수정한다.

```text
프놌펜 → 프놈펜
```

기능 예시와 후기 반복 데이터 모두 포함한다. 현재 검색 입력창 placeholder의 `프놈펜`은 정상이며 그대로 둔다.

### 9.2 데모 고지 정책

프론트 본문에서 다음 유형의 문구를 제거한다.

- `데모용 예시 후기입니다...`
- `데모용 예시 데이터입니다...`
- 카드, 차트, 후기 영역 안의 데모·가상 데이터 설명

단, **푸터 최하단의 작은 데모 고지는 유지**한다.

유지 문구:

```text
본 화면은 디자인 검토용 데모이며, 게재된 자산·가격·정보는 실제 서비스와 다를 수 있습니다.
```

푸터의 다른 법인·운영 주체 문구는 변경하지 않는다.

준비 중 페이지의 기능 상태 설명은 데모 고지가 아니라 서비스 상태 안내이므로 유지할 수 있다. 다만 `이 데모에는...`처럼 데모 자체를 설명하는 문장은 `현재 준비 중인 기능입니다.` 계열로 바꿔 제안한다.

## 14. 완료 기준

다음 항목을 모두 충족해야 디자인 완료로 판단한다.

- 랜딩에서 AI 탐색 CTA가 첫 번째 행동으로 명확히 보인다.
- 랜딩에 실제 검색 입력창·필터·검색 결과가 없어 탐색 페이지와 중복되지 않는다.
- `/explore`에서만 실제 검색과 결과 UI가 제공된다.
- 검색 진행 단계의 idle/active/done/error 상태를 시각적으로 구분할 수 있다.
- 모바일에서 현재 진행 단계를 한눈에 이해할 수 있다.
- 360px, 390px, 430px에서 가로 넘침과 제목·가격 겹침이 없다.
- 모바일 입력 글자가 16px 이상이다.
- CTA와 주요 터치 영역이 48px 이상이다.
- 자동 이동 콘텐츠가 reduced-motion, hover, focus 상태에서 멈춘다.
- `프놌펜`이 남아 있지 않다.
- 본문 데모 고지는 제거되고 푸터의 작은 고지만 남는다.
- 기존 브랜드 컬러, 폰트, 자산 데이터와 사업 정책이 바뀌지 않는다.

## 15. 변경 전 보고가 필요한 항목

다음 사항은 Claude가 먼저 별도 목록으로 제안하고 사용자 승인을 받은 뒤 적용한다.

- 새로운 섹션 추가 또는 기존 섹션 삭제
- 랜딩 헤드라인 변경
- CTA 확정 문구 변경
- 모바일 고정 CTA 추가
- 상세 페이지 하단 고정 행동 영역 추가
- 내비게이션 메뉴 항목의 추가·삭제·순서 변경
- 새로운 이미지 생성 또는 기존 대표 이미지 교체
- 이 문서에 없는 카피 변경

Claude는 최종 전달 시 `IMPLEMENTATION-NOTES.md` 첫 부분에 **원본과 육안으로 달라진 모든 요소**를 목록으로 기록한다.

## 16. 토큰·작업시간 절약을 위한 전달 규칙

Claude 결과를 Codex가 다시 해석하거나 디자인을 재작성하지 않는다. 다음 방식으로 전달한다.

### 기본 원칙

- Claude는 React 코드를 만들지 않는다.
- Codex는 Claude HTML을 화면별로 다시 디자인하지 않는다.
- 최종 HTML/CSS/시안 JS는 파일로 전달하고, Codex는 파일을 기계적으로 교체한다.
- Codex는 전체 파일을 대화에 출력하거나 전부 읽지 않고 `git diff`의 변경 구간만 검토한다.
- 자동 생성 파일은 Claude가 전달하지 않는다. Codex가 원본을 받은 뒤 생성기를 실행한다.

### Claude가 전달할 최소 파일

```text
source/gli-demo.dc.html             # 최종 전체 원본
source/public/...                   # 새로 추가하거나 실제로 변경한 자산만
CHANGELOG-2026-08-12.md             # 변경한 위치와 이유
IMPLEMENTATION-NOTES.md             # 이벤트·상태 계약
FILE-HASHES.txt                     # 전달 파일 SHA-256
```

`README.md`, `DESIGN-RULES.md`, `DEMO-DATA.md`, `ASSETS.md`는 실제 내용이 달라졌을 때만 다시 전달한다.

다음 파일은 전달하지 않는다.

- React/Next.js 변환본
- `app/generated/claude-static.ts`
- 빌드 결과물
- `node_modules`
- 기존과 동일한 이미지의 중복본
- 별도 요청이 없는 고해상도 전체 페이지 캡처

### CHANGELOG 필수 형식

```markdown
## 변경 파일
- source/gli-demo.dc.html

## 변경 구역
- LANDING HERO: CTA 위계 및 모바일 순서
- EXPLORE PIPE: idle/active/done/error 상태
- MOBILE: 검색 버튼, 질문 칩, 메뉴
- ACCESSIBILITY: ticker/marquee 정지 규칙
- COPY: 프놌펜 오타, 본문 데모 고지

## 새 이벤트 또는 클래스
- 없음 또는 정확한 이름과 전달 값

## 의도적으로 변경하지 않은 영역
- 자산 데이터
- 멤버십
- 상세 정보 구조
```

### Codex 수령 절차

1. 전달 파일의 SHA-256을 확인한다.
2. 현재 소스를 별도 커밋으로 보존한다.
3. 전달 파일을 동일 경로에 덮어쓴다.
4. 전체 원본이 아니라 `git diff --word-diff=porcelain`과 변경 구간만 검토한다.
5. 승인 범위를 벗어난 변경이 있으면 구현하지 않고 사용자에게 보고한다.
6. 디자인 생성기를 실행한다.
7. React 이벤트와 API만 연결한다.
8. 지정된 PC·모바일 화면만 비교 검수한다.
9. 테스트 통과 후 로컬 URL을 제공한다.
10. 사용자 승인 전 공개 배포하지 않는다.

### 전달 효율 판단

다음 중 하나에 해당하면 Codex는 작업 전에 사용자에게 토큰·시간 낭비 가능성을 알린다.

- Claude가 변경 이력 없이 전체 프로젝트를 다시 전달한 경우
- 동일 이미지와 생성 파일이 반복 포함된 경우
- HTML과 React 구현이 함께 전달되어 어느 쪽이 기준인지 불명확한 경우
- 승인 범위를 넘어 다수의 문구·데이터·페이지 구조가 변경된 경우
- 단순 CSS 수정인데 전체 화면을 수작업으로 다시 구현해야 하는 형태인 경우

이번 구조에서는 `source/gli-demo.dc.html`이 유일한 디자인 기준이며, Codex 생성기가 이를 React용 정적 화면으로 변환한다. 따라서 위 전달 규칙을 지키면 후속 디자인 반영은 전체 재개발이 아니라 **변경분 검토 + 자동 생성 + 이벤트 연결** 작업으로 처리한다.
