## 전달받은 답변 원문

GLI 탐색·상담 아키텍처 자문
0. 가장 큰 문제와 잘못된 전제부터
1. 현재 가장 큰 병목은 모델이 아니라 오케스트레이션입니다.
Gemini 30초 타임아웃으로 탐색이 중단됐다는 것은 사용자 요청 -> GPT 해석 -> Gemini 탐색 -> 병렬 수집 -> DB조회 를 동기 직렬로 묶었다는 증거입니다. 사용자는 Top5를 보기 위해 외부 크롤러가 끝날 때까지 기다릴 이유가 없습니다. 데모 구조는 "수집이 끝나야 상담이 시작된다"는 전제를 깔고 있습니다. 반대로 가야 합니다: 상담은 즉시 DB로 시작하고, 외부 탐색은 백그라운드로 보강합니다.

2. "수집 건수 = 후보 풍부도" 라는 착시
세 국가 포털 수집이 성공해도, 그게 순수익 근거가 있는 후보 5개가 된다는 보장은 없습니다. 현재 파이프라인은 목록 수집은 되는데, 임대수익 추정을 위한 임대료/공실률/운영비 필드는 비어 있습니다. 이 상태로 Gemini를 붙여도, 웹에서 찾은 가격 불명확한 매물이 DB를 오염시킵니다. 먼저 데이터 계약을 고쳐야 합니다.

3. GPT와 Gemini 역할 분담의 오류
"GPT=상담, Gemini=탐색"으로 나누면, 두 모델이 같은 사용자 의도를 각자 해석하게 되어 일관성이 깨집니다. 의도 해석은 Single Source of Truth가 1개여야 합니다. 번역/태그화/메타데이터 선별은 LLM이 할 일이 아닙니다. 정규식/룰/임베딩이 더 빠르고 저렴하고 결정론적입니다.

수정된 전제
서버가 Intent와 Truth를 소유한다. LLM은 서버가 만든 구조화된 Context를 소비하는 Reasoning / Generation 레이어다.
사전 수집이 기본값, 검색 시 수집은 예외 처리다.

2. AI vs 코드 구분 - 자문 질문 1, 12
코드로 해야 할 영역:

모든 필터링, 환율, 가격 환산, 면적 변환, 중복 제거, 출처 신뢰도 점수
가정 가능 vs 필수 확인 구분 룰 엔진. LLM에게 맡기면 매번 기준이 흔들립니다.
국가/예산/수익유형 파싱의 1차 시도. LLM은 2차 검증용.
LLM이 해야 할 영역:

모호한 의도 해석: "월 300 버는" = 순수익? 매출? GPT가 income_target: net으로 가정 생성
근거 기반 설명 생성, 후보 비교 서술
다음 질문 선정 - 단, 서버가 만든 정보 이득(Information Gain) 후보 중 1개를 고르게 함. LLM이 자유 생성하면 엉뚱한 질문을 합니다.
제3의 모델/결정 전용 AI는 필요한가? - 질문 12
지금은 불필요합니다. JEV를 결정 전용으로 키우는 것보다 서버에 Decision Table을 두는 것이 검증 가능합니다. 추가 호출 효과를 검증할 실험:

실험: 동일 Intent에 대해 (a) GPT가 다음 질문 자유 생성 vs (b) 서버가 부족한 슬롯 3개를 주고 GPT가 1개 선택. 100회 상담 로그에서 불필요한 질문 수, 사용자 수정 횟수 비교.

4. 예산 없는 질문 처리 - 질문 3
"캄보디아에서 월 300만원 버는 부동산"

순서:

서버가 먼저 역산: 관측 환율 + 국가별 cap rate 추정 범위(예: KH 6∼9%) + 운영비 20% 가정으로 필요 투자금 범위 계산. 300만원 / 0.07 / 0.8 = 약 6.4억 . 이건 코드 계산.
보여줄 것: "월 300만원 순수익 가정으로, 필요 투자 규모는 약 5∼7억으로 추정됩니다 [가정]" + DB에서 그 투자 규모에 맞는 Top5 (수익 근거 등급 표시)
확인 질문: "300만원은 운영비·공실 제외한 순수익 기준이 맞을까요? 투자 가능 예산을 6억대로 봐도 될까요?" - 1개만.
절대 예산을 임의로 만들지 말고, 역산 범위를 가정으로 제시.

가정 vs 필수 확인 기준 - 질문 4

가정 가능: 사용자의 편의를 위한 기본값, 틀려도 치명적이지 않은 것. 예) 월수입=순수익, 거주 목적 없음, 관리 대행 선호, 1개 물건 기준. 반드시 editable chip으로 보여줌.
필수 확인: 틀리면 Top5 전체가 무효가 되는 것. 예) 국가, 법인 보유 가능 여부, 총 예산 상한, 대출 불가 조건. 이건 바꾸면 안 됨.
기준: 해당 조건을 잘못 가정했을 때 후보의 80% 이상이 필터 아웃되는가? -> 그렇다면 필수 확인.

중복/변경 판별 - 질문 8
키: source + external_id 가 1차키. 없으면 normalized_address + area_m2 + floor 해시 = identity_hash.
비교 절차:

identity_hash 동일 + 가격 10% 이내 + 면적 5% 이내 -> 동일 매물
동일 매물인데 source 다름 -> 출처 병합, 신뢰도 높은 출처를 canonical
동일 매물인데 가격/상태 변경 -> change_log 테이블에 이력, first_seen_at != last_seen_at
절대 제목 유사도만으로 중복 판단 금지.

실패 구분 상담 문구 - 질문 9

수집 실패: "캄보디아 A 포털 점검이 있어 신규 매물 확인이 지연되고 있습니다. 현재 DB 312건 기준으로 보여드립니다."
정상 조회 0건: "조건에 맞는 수집 소스가 없습니다. 국가를 넓히거나..."

수익 근거 부족: "후보 3건은 예산에 맞으나 임대 근거가 미확인이라 Top5에서 제외했습니다. 임대료 확인 후 재포함할까요?"
시장 전체에 없다고 단정 금지.

6. 근접 후보 기준 - 질문 6
보여주는 기준: 필수 조건 1개만 15% 이내로 벗어나고, 나머지는 모두 만족하며, net_yield_confidence > 0.6 일 때. 예) 예산 6억인데 6.8억 물건이 수익률이 월등히 높음.

보여주지 않는 기준: 필수 조건 2개 이상 위반, 또는 국가 위반, 또는 missing 데이터로 간신히 끼워 맞춘 경우. Top5를 채우려고 근접 후보로 메우지 마세요. 3개만 보여주는 게 신뢰가 높습니다.

UI: 정확 부합 3건 + 조건 완화 시 고려 가능 2건(예산 +15%) 으로 섹션 분리.
