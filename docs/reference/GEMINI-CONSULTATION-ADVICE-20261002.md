## 전달받은 답변 원문

현재 설계안에서 가장 시급히 해결해야 할 치명적인 위험 요소는 '사용자 상담 세션 내에서의 실시간 외부 웹 탐색(Gemini)'입니다.

사용자가 답변을 기다리는 수 초 내에 외부 출처 접속, 차단 우회, 스크래핑, 텍스트 구조화, 번역, 검증을 모두 완료하려는 접근은 본질적으로 실패 확률이 높습니다. 30초 타임아웃은 필연적인 결과이며, 응답 지연은 최악의 사용자 경험을 초래합니다. 외부 웹 탐색과 사용자 상담은 완전히 분리된 비동기(Asynchronous) 프로세스로 설계되어야 합니다. 또한, 수치 비교와 필수 조건 필터링을 AI에게 맡기는 것은 환각(Hallucination)과 누락의 원인이 되므로 일반 코드로 격리해야 합니다.

## 1. 권장 아키텍처 및 대안 비교

목표는 두 모델의 직렬 호출을 최소화하고, 서버가 결정적(Deterministic) 로직을 통제하며, AI는 의도 파악과 결과 설명에만 집중하는 것입니다. 제3의 모델이나 결정 전용 AI는 불필요한 지연과 비용만 발생시키므로 도입하지 않습니다. 서버의 일반 코드가 라우터 역할을 하는 것으로 충분합니다.

| **구분**        | **권장 아키텍처 (비동기 캐시-우선 기반)**                | **단순 대안 아키텍처 (완전 사전 수집 기반)**        |
| ------------- | ----------------------------------------- | ----------------------------------- |
| **핵심 구조**     | 사전 수집 DB 조회로 즉각 응답 + 필요시 백그라운드 탐색         | 외부 탐색 없이 오직 주 1회 사전 수집된 DB 내에서만 상담  |
| **GPT의 역할**   | 의도 추출, 가정 설정, 서버가 반환한 DB 결과의 설명 및 비교      | 질문 의도 파악 및 DB 결과 포장                 |
| **Gemini 역할** | 백그라운드 워커: 스케줄러에 의한 메타데이터 추출, 번역, 태그화      | 배치(Batch) 파이프라인 전용 번역/추출기           |
| **서버의 역할**    | DB 조회, 수치 필터링, 백그라운드 작업 큐 관리, API 타임아웃 방어 | 단순 CRUD, 하드 필터링 로직 수행               |
| **장점**        | 사용자는 대기 없이 즉각 답변을 받으며, 최신성은 백그라운드에서 보완    | 구조가 매우 단순하고 서버 인프라 비용/장애 포인트가 적음    |
| **단점**        | 상태 관리(보류 중인 탐색 작업) 및 UI 동기화 복잡도 증가        | 최신 매물 확보 불가능, 매물 거래 완료 여부 실시간 확인 불가 |

## 2. 데이터 수집 및 사용자 상담 흐름도

데이터 수집(Gemini + Server)과 상담(GPT + Server)의 라이프사이클을 완전히 분리합니다.

### A. 데이터 수집 및 저장 흐름 (백그라운드 파이프라인)

1. **타겟 식별:** 서버 스케줄러가 대상 포털/출처의 목록 페이지 URL을 확보.
2. **원시 데이터 수집:** 서버가 HTML/JSON 크롤링 (차단 방지는 프록시/서버 레벨 처리).
3. **구조화 및 번역 (Gemini):** 수집된 원시 텍스트를 Gemini에 입력하여 정해진 JSON 스키마(가격, 위치, 면적, 특징 등)로 추출 및 한국어 번역.
4. **식별 및 중복 제거 (Server):**
   - **식별 키(Hash):** `SHA256(국가 + 도시 + 아파트/건물명 + 면적 + 층수구간)`
   - 기존 DB에 동일 해시가 있으면 `Update` (가격 변동, 상태 변경 기록), 없으면 `Insert` (처음 본 매물). 출처가 달라도 해시가 같으면 동일 매물로 병합.
5. **DB 저장:** D1 (향후 AWS RDS/DynamoDB) 저장.

### B. 사용자 상담 흐름 (대기 시간 3초 이내 목표)

1. **의도 파악 (GPT):** 사용자 입력 분석. 조건(명시적/가정)을 JSON으로 서버에 전달.
2. **하드 필터링 (Server):** GPT가 넘긴 JSON 조건을 바탕으로 SQL 쿼리 실행. 환율 계산, 1차 조건 부합 필터링 수행.
3. **유효성 퀵 체크 (Server - 선택적):** 선별된 Top 5 매물에 대해 출처 URL의 HTTP Header/상태코드만 빠르게 핑(Ping)을 때려 삭제된 페이지인지 확인. (1초 이내)
4. **응답 생성 (GPT):** 서버가 반환한 Top 5 데이터와 실패/상태 코드를 바탕으로 사용자에게 제공할 설명, 비교, 후속 질문 생성.

## 3. 각 단계의 입력, 출력 및 실패 처리

### [Step 1] 사용자 의도 해석 및 조건 추출 (GPT)

- **입력:** 사용자 질문, 이전 대화 상태(Context).
- **출력 (JSON):** `{"mandatory": {"country": null, "budget_max_krw": null}, "assumed": {"yield_percent": 6, "property_type": "condo"}, "intent": "investment"}`
- **특수 상황 처리 (예: "월 300만원 수익"):** 명시적 예산이 없을 경우, GPT는 현지 평균 수익률(예: 6%)을 `assumed`로 설정하여 역산된 예산(약 6억 원)을 출력에 포함.
- **실패/예외:** 모호함이 너무 커서 쿼리 생성이 불가능할 경우 `needs_clarification: true` 반환 후 즉시 단일 후속 질문으로 전환.

### [Step 2] 데이터베이스 검색 및 필터링 (Server)

- **입력:** Step 1의 JSON 객체.
- **출력 (JSON):** 정확도 순 Top 5 후보 배열, 검색 메타데이터(상태 코드).
- **데이터 계약 (Data Contract) 적용:** 수익률(ROI)의 신뢰도를 강제합니다.
  - `"roi": {"value": 5.0, "type": "fact", "basis": "실제 임대 계약서"}`
  - `"roi": {"value": 5.5, "type": "estimate", "basis": "동일 단지 최근 3개월 평균"}`
  - `"roi": {"value": null, "type": "unconfirmed", "basis": "데이터 없음"}`
- **근접 후보 노출 기준:** 정확한 조건 부합 매물이 3개 미만일 때, 예산이나 면적 오차율 15% 이내의 매물을 포함시킵니다. (국가 등 필수 조건 위반은 절대 제외). 포함 시 `near_match_reason: "예산 5% 초과"` 태그를 붙여 UI/UX에서 시각적으로 분리하도록 합니다. 부합하는 것이 아예 없으면 빈 배열을 반환합니다.

### [Step 3] 답변 생성 및 후속 질문 선정 (GPT)

- **입력:** Step 2의 검색 결과 배열 및 상태 코드, 기존 대화.
- **상태 코드별 분기 (구분 기준):**
  - `ERROR_DB_TIMEOUT`: 시스템 문제. "현재 데이터베이스 접속이 지연되고 있습니다."
  - `ZERO_SCRAPED`: 지역 내 데이터 자체가 없음. "해당 국가/지역에 수집된 매물 데이터가 없습니다."
  - `ZERO_MATCH`: 매물은 있으나 조건 부합 안 함. "매물은 있으나, 요청하신 예산(또는 조건)에 부합하는 항목이 없습니다."
  - `ROI_UNCONFIRMED`: "조건에 맞는 매물을 찾았으나, 실제 임대 수익이 증명된 자료가 부족하여 추정치로 제공합니다."
- **가정 조건 안내:** "현지 평균 수익률 6%를 가정하여, 약 6억 원 규모의 매물을 기준으로 탐색했습니다. 이 예산 범위가 적절하신가요?" 형태로 출력.
- **출력:** 최종 설명, Top 5 리스트(명확한 근거 포함), **단 1개의 후속 질문**.

## 4. 엣지 케이스 및 UX 전략

**Gemini 외부 탐색 지연/실패 시 전략 (UI 변경 방지)**

실시간 Gemini 탐색을 배제했으므로 대기(Spinner)나 부분 결과 제시로 인한 UX 피로도 문제는 해결됩니다. 만약 사용자가 "어제 올라온 최신 매물 찾아줘"라고 명시적으로 요구할 경우, GPT는 DB 결과를 우선 보여준 뒤 "현재 새로운 매물이 있는지 백그라운드에서 추가 탐색을 시작했습니다. 확인되면 알림으로 알려드리겠습니다."라고 응답하고 대화 턴을 종료합니다. UI가 비동기적으로 렌더링되도록 처리해야 사용자의 선택을 방해하지 않습니다.

**조건의 구분 기준 (가정과 필수)**

- **가정 가능 조건:** 예산(목표 수익금만 있을 때 역산), 수익률, 부동산 형태(콘도/아파트), 세금 조건. (가정 시 반드시 사용자에게 명시하고 수정할 수 있는 UI/후속 질문 제공).
- **반드시 확인해야 하는 조건:** 국가(투자 타겟), 실거주 vs 순수 투자 여부. (이 두 가지가 없으면 검색 범위가 무한대에 가까워지므로 반드시 후속 질문으로 확인).

**상담 상태(State) 관리**

세션 DB(Redis 등)에 다음 상태를 유지해야 후속 질문 시 전체 재검색을 방지할 수 있습니다.

- `explicit_conditions`: 사용자가 확정한 조건.
- `assumed_conditions`: AI가 임의로 설정한 조건.
- `shown_candidates_hashes`: 이미 사용자에게 제시된 매물의 해시 배열 (동일 매물 반복 제시 방지).
- `pending_async_jobs`: 백그라운드 탐색 중인 작업 ID.

## 5. 우선순위별 개선안 및 검증 실험

**개선 1순위: 탐색 파이프라인 분리**

현재의 GPT-Gemini 병렬 탐색 후 취합 구조를 즉각 폐기하고, Gemini를 크론(Cron) 기반의 백그라운드 적재 파이프라인으로 이동시킵니다.

**개선 2순위: 데이터 계약(Data Contract) 기반 스키마 확정**

DB에 저장되는 매물 정보에 `roi_type` (fact/estimate/unconfirmed) 필드를 강제하고, GPT 프롬프트가 이를 기반으로만 수익률을 언급하도록 제약합니다. 근거 없는 수익률 주장을 원천 차단할 수 있습니다.

**검증 실험 제안**

- **의도 추출 속도 및 정확도 A/B 테스트:** 사용자 질문을 JSON 조건으로 파싱하는 Task에 대해 GPT-4o-mini와 Claude 3.5 Haiku(또는 Sonnet)를 1,000건의 테스트 셋으로 비교합니다. 라우팅과 파싱은 속도가 생명이므로, 더 빠르고 JSON 형식을 엄격히 지키는 모델을 Step 1에 배치합니다.

**평가 지표 (KPIs)**

1. **첫 유용한 답변까지의 시간 (Time to First Meaningful Paint):** 목표 3초 이내. (외부 탐색 제거로 달성 가능)
2. **전체 응답 시간 (Total Turnaround Time):** 목표 5초 이내.
3. **후보 적합성 (Candidate Fit Score):** 제시된 Top 5 중 필수 조건을 만족하는 비율 (목표 100%).
4. **불필요한 질문 수:** 명시된 조건이나 합리적 가정이 가능한데도 되묻는 횟수 (목표: 세션당 0회).
5. **근거 없는 주장 (Hallucination Rate):** Fact/Estimate 데이터 계약을 위반하고 확정 수익률로 응답한 비율 (목표 0%).
6. **사용자 수정 횟수:** AI의 가정을 사용자가 정정하는 횟수 (낮을수록 초기 가정 모델이 우수함).
7. **상담당 비용 (Cost per Session):** LLM 토큰 비용 및 서버 처리 비용 합산. (동기적 웹 탐색을 제거하면 토큰 낭비가 획기적으로 감소함).
