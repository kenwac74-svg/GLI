GLI 탐색·상담 아키텍처 자문
0. 가장 먼저: 잘못된 전제와 가장 큰 문제
잘못된 전제 ① — "외부 웹 탐색이 상담의 동기 경로에 있어야 한다."
현재 구조의 가장 큰 문제이며, 최근 테스트의 30초 중단은 모델 문제가 아니라 이 전제의 결과입니다. 웹 탐색은 본질적으로 지연·실패 변동성이 크고, Google Search grounding은 호출당 과금(유료 티어에서 Gemini 3.x 기준 월 5,000건 무료 후 1,000건당 $14)되는 외부 의존 자원입니다. 이것을 사용자가 응답을 기다리는 동기 경로에 두는 한, 응답 시간과 성공률은 항상 외부 상태에 인질이 됩니다. 웹 탐색은 수집 파이프라인(비동기)의 일부여야 하고, 상담 경로는 DB와 규칙 엔진만으로 완결되어야 합니다.
잘못된 전제 ② — "역할 분담은 모델 두 개의 특성 차이에서 나온다."
제안하신 분담을 보면 GPT와 Gemini의 실질적 차이는 "Gemini가 Google Search grounding과 URL context를 갖는다"는 점 하나입니다. 그런데 OpenAI에도 웹 검색 도구가 있고(1,000회당 $10 + 검색 콘텐츠 토큰 과금), URL context는 입력 토큰으로만 과금됩니다. 즉 분담의 근거가 "모델 능력"이 아니라 "어느 벤더의 검색 도구를 쓸 것인가"인데, 이 판단 없이 이중 모델 운영(프롬프트 2세트, 출력 형식 2세트, 일관성 검증, 장애 도메인 2개)을 받아들이고 있습니다. 두 모델 병용의 이득은 측정으로 입증해야 할 가설이지 기본값이 아닙니다.
가장 큰 실질 문제 — 수익 근거의 부재가 아키텍처 문제가 아니라 수집 스키마 문제.
"월 300만원 버는 부동산"이라는 핵심 요청을 처리하려면 임대료·공실률·운영비가 필요한데, 현재 출처에서 이 데이터가 안 나온다면 이는 Gemini/GPT 배치를 어떻게 하든 해결되지 않습니다. (a) 수집 출처 확장(임대 매물 출처 병행 수집으로 임대 시세 추정), (b) "수익 근거 없음"을 일등 시민으로 표현하는 데이터 계약, 이 둘이 모델 편성보다 먼저입니다.
잘못된 전제 ③ — "JEV 활용 확대"가 아젠다에 오른 것 자체.
스스로 "활용 확대가 목적이 아니다"라고 쓰셨듯, 확인 질문 판단은 규칙 + 단일 분류 호출로 충분한 영역입니다. 별도 판단 계층을 유지할 근거가 보이지 않습니다(후술).
1. 권장 아키텍처 vs 더 단순한 대안
권장안: "서버 오케스트레이터 + 비동기 수집 + 2-콜 상담"
핵심 원칙: AI는 상태를 소유하지 않는다. 모든 판단 상태와 조건은 서버 DB에, AI는 무상태(stateless) 작업 단위로만 호출된다.
수집 파이프라인(비동기): 출처 수집기(코드) → 정규화(코드+AI 구조화) → 중복 판정(코드) → DB. 웹 탐색·번역·비정형 페이지 구조화에만 AI 사용. 배치·오프피크 실행.
상담 경로(동기, 최대 AI 2회 호출):
콜 A(의도 파싱): 사용자 발화 → 구조화 출력으로 슬롯 추출(국가/예산/목적/목표수익 + hard/soft 구분 + 후속질문 유형 분류).
서버 중간 처리: 슬롯 검증·가정 채우기 → DB 쿼리·필터·정렬·수익 계산(전부 코드) → Top5 선정.
콜 B(답변 생성): 선정된 후보 + 가정 목록 + 데이터 provenance → 설명문, 후보 비교, 후속 질문 1개 생성. 후보 선택·계산은 하지 않고 표현만 담당.
더 단순한 대안: "단일 모델 상담 + 기존 출처 배치 수집"
상담 경로는 GPT 단독(동일한 2-콜 구조), 수집은 기존 국가별 수집기만으로 운영하고 Gemini 웹 탐색 단계를 통째로 빼거나 주 1회 배치로 축소.
포기하는 것: 검색 시점의 신규 매물 발견 범위. 얻는 것: 벤더 1개, 프롬프트 1세트, 장애 모드 절반, 비용 절감.
이 대안이 현실적인 이유: 어차피 "모든 포털을 수집하는 것이 아님"을 이미 인정했고, 커버리지 한계는 UX 문구로 처리하기로 했으므로, 웹 탐색이 추가하는 커버리지가 상담 품질에 기여하는 크기는 측정 전에는 알 수 없습니다. 권장안과 대안을 A/B로 돌려 Gemini 탐색의 후보 적합성 기여분을 측정하고, 기여가 작으면 대안으로 수렴시키는 것이 합리적입니다.
2. 두 개의 흐름 (분리 도식)
흐름 A — 데이터 수집·저장 (비동기, 사용자와 무관하게 주기 실행)
plain
[출처 스케줄러: 출처별 주기 6~24h, 코드]
        │
        ▼
[목록 수집: 수집기 코드 / 필요 시 Gemini 웹탐색·URL context]
        │  ─ 실패 시: 출처 상태를 degraded로 표시, 지수 백오프 재시도
        ▼
[정규화: 코드(통화·면적 단위) + Gemini(비정형 상세→JSON, 번역·태그)]
        │  ─ 구조화 실패 시: raw 저장 + reprocess 큐
        ▼
[중복 판정: 정확키(출처+출처ID) → 콘텐츠 해시 diff → 유사 매물 클러스터]
        │  구분 결과: 신규 / 기존 매물 변경(버전↑) / 타 출처 동일 매물(병합 후보 큐)
        ▼
[D1 저장: listing_version, provenance(필드별 verified/estimated/unknown), 수집시각]
        │
        ▼
[수익 근거 보강 잡: 임대 시세 추정치 계산 → estimated로 태그]
흐름 B — 사용자 상담 (동기, 목표: 첫 유용 답변까지 수 초)
plain
[사용자 발화]
   │
   ▼
[AI 콜 A: 의도·슬롯 파싱(구조화 출력)] ─ 실패 시: 슬롯 추출 규칙 폴백 + "조건을 다시 확인" 문구
   │  출력: {hard조건, soft조건, 질문유형(신규/설명/비교/조건변경)}
   ▼
[서버: 슬롯 검증 → 가정 채우기(가정 테이블, 수정 가능 표시) → DB 쿼리
        → 필수조건 필터(코드) → 수익 계산(관측 환율, 코드) → 정렬 → Top5 + 근접후보]
   │  ─ 조건 부합 0건 시: 완화 제안 목록 생성(코드)
   ▼
[AI 콜 B: 답변 생성 — 결론, Top5 설명(근거 링크), 가정 명시, 후속 질문 1개]
   │  ─ 실패 시: 서버가 카드형 기본 템플릿으로 후보만이라도 제시(무응답 방지)
   ▼
[응답]  + [백그라운드: 목록 신선도 재확인 잡 등록 — 결과는 다음 턴에 "변경 알림"으로]
핵심: 흐름 B에는 웹 탐색이 없습니다. 신선도는 "마지막 확인 시각" 라벨로 투명하게 표시하고, 재확인은 백그라운드로 처리합니다.
3. 12개 질문에 대한 답변
Q1. 역할 분담 적절성 / AI vs 코드 경계
시트
영역	담당	이유
의도 해석, 슬롯 추출	AI(GPT)	비정형 자연어
가정 설정	코드(가정 테이블) 우선, AI는 문구만	가정은 재현 가능하고 감사 가능해야 함
필수조건 필터링, 환율, 수익 계산, 정렬	코드(절대 AI 아님)	이미 그렇게 하고 있으며 정답
비정형 웹 페이지 → JSON 구조화, 번역, 태그	AI(Gemini 또는 단일 모델)	코드 파서 유지보수 대비 유연

출처 검증, 일정, 상태 관리	코드	이미 정답
즉 제안하신 분담의 방향은 맞고, 조정점은 두 가지입니다: ① "가정 설정"은 AI가 아니라 서버의 가정 테이블이 소유하고 AI는 사용자에게 보여줄 문구만 생성, ② Gemini에 배정된 역할은 "Gemini라서"가 아니라 "웹 접근 도구가 필요해서"이므로 도구 기준으로 재명명할 것.
Q2. 직렬 호출 최소화 실행 순서
위 흐름 B 그대로입니다: 콜 A(파싱) → 서버 처리 → 콜 B(표현). 총 2회 직렬. 일관성은 대화 맥락을 두 콜에 동일하게 주입하는 것이 아니라, 서버가 보유한 상담 상태 객체(Q11)를 콜 B의 입력으로 넣는 방식으로 유지합니다. 콜 A와 콜 B 사이에 판단이 갈라질 여지는 서버의 결정론적 처리가 흡수하므로 모델 간 맥락 전달 문제 자체가 사라집니다. 콜 A 없이 콜 B만으로 처리 가능한 턴(설명·비교 요청)은 콜 A를 건너뜁니다 — 턴 분류는 가벼운 규칙으로 선판정.
Q3. 예산 없는 "월 300만원 버는 부동산" 질문의 처리 순서
서버가 역산 먼저: 목표 월 순수입 300만원 → 연 3,600만원. DB 내 해당 국가 후보들의 추정 순수익률 분포(estimated 태그)에서 필요 투자금 범위를 역산. 예: "현재 확보 자료 기준 순수익률 추정 X~Y% → 필요 투자금 약 Z1~Z2억 원(추정)".
제시할 것: (a) 역산된 필요 투자 규모, (b) 그 규모대의 근접 후보 몇 건 — 수익 근거가 estimated임을 명시.
후속 질문 1개: "예산 범위를 알려주시면 후보를 실제 조건으로 좁힐 수 있습니다" — 확인 질문이지만 후보 제시 후에 옵니다.
"순수입" 가정(임대수입−운영비, 공실 반영 여부 명시)은 가정 테이블에 등록하고 한 줄로 고지. 확인 질문을 먼저 던져 후보 제시를 미루는 순서는 요청하신 경험 원칙에 위배됩니다.
Q4. 가정 vs 필수 확인의 구분 기준
세 가지 기준의 조합:
결과 민감도: 가정이 틀렸을 때 Top5가 완전히 바뀌는가? (국가, 투자 vs 거주 목적 → 민감 → 미명시 시 확인)
사용자 명시 여부: 명시된 조건은 무조건 hard(임의 변경 금지, 기존 원칙과 동일).
수정 비용: 한 줄로 고치기 쉬운가? (통화 기준, 면적 기준, 수익률 산정 방식 → 가정+표시로 진행)
실무 규칙: hard가 아니면서 민감도 낮고 수정 쉬운 것 → 가정. 민감도 높고 미명시 → 확인 질문(단, Q3처럼 후보 제시와 동시에 묻는 형태 우선). 이 판정은 모델이 매번 추론하는 것이 아니라 슬롯별로 미리 정한 정책 테이블로 처리하고, 경계 사례만 콜 A 출력의 confidence로 판단.
Q5. 확인된 사실·추정·미확인의 데이터 계약
필드 단위 provenance를 권장합니다. 매물 레코드의 각 필드가 다음을 가집니다:
plain
{ value, status: "verified" | "estimated" | "unknown",
  source: <출처 식별자>, observed_at: <시각>,
  method: <estimated일 때 추정 방법, 예: "동일 단지 임대 매물 중앙값"> }
그리고 파생 규칙 하나: 계산 필드(순수익률 등)의 status는 입력 필드들의 최악 status를 상속. 임대료가 estimated면 수익률도 estimated. unknown이 하나라도 끼면 해당 지표는 "산정 불가 — 무엇이 확인되면 가능한지"를 명시. 이 계약만 있으면 콜 B가 "근거 없는 주장"을 생성할 여지가 구조적으로 줄고, 평가 지표의 '근거 없는 주장률' 채점도 자동화할 수 있습니다.
Q6. 근접 후보 제시 기준 / 미제시 기준
제시 기준: (a) 위반한 조건이 사용자 명시 hard 조건이 아니고, (b) 편차가 사전 정의된 임계 이내(예: 예산 ±10%, 면적 ±15% — 임계값은 정책 테이블에 명시, 수치는 튜닝 대상 가설), (c) 어떤 조건이 얼마나 어긋나는지 카드에 명시, (d) 정확 부합 후보와 시각적으로 구분된 섹션.
미제시 기준: hard 조건 위반(국가·목적), 임계 초과, 그리고 정확 부합 0건인데 근접만 5건으로 Top5를 채우는 경우 — 이때는 근접 후보를 "근접 후보"로 라벨링해 최대 3건까지만 보여주고 나머지 자리는 "조건 완화 제안"으로 채웁니다.
Q7. 사전 수집 + 재확인 + 상세 수집의 조합
사전 수집: 출처별 6~24시간 주기(변경 빈도 측정 후 조정 — 측정 항목).
검색 시 목록 재확인: 동기로 하지 않고, 응답 즉시 백그라운드 잡으로 "제시된 Top5의 출처 페이지 생존·가격 변경"만 확인(전체 재탐색 아님). 결과는 다음 턴의 "변경 알림"으로.
상세 수집: 사용자가 후보를 열어보거나 비교를 요청한 시점에 해당 후보만 상세 수집(관심 신호 기반 lazy 수집). 이렇게 하면 웹 접근 비용이 상담당 상수가 아니라 관심 후보 수에 비례하게 됩니다.
Q8. 신규 / 변경 / 타 출처 동일 매물 구분
1단계(정확): listing_key = (source_id, source_listing_id). 키 미존재 → 신규.
2단계(변경): 키 존재 시 정규화 필드의 콘텐츠 해시 비교. 단, 모든 필드 diff가 아니라 의미 필드(가격, 상태, 면적) 변경만 버전 증가 + 이벤트 기록, 노이즈 필드(이미지 순서 등)는 무시 목록으로 제외. 수집 시각과 게시 시각을 별도 필드로 분리(요청서 제약과 일치).
3단계(타 출처 동일 매물): 정규화 속성 규칙 매칭(좌표 반경, 건물명 정규화, 면적·가격 근접)으로 후보 쌍 생성 → 임베딩 유사도 상위 쌍만 병합 후보 큐 → 자동 병합은 confidence 임계 이상만, 나머지는 보류. 병합 결과는 하나의 canonical 매물에 다수 출처를 sources[]로 매달고, 출처별 원문은 보존(판정 근거 감사용).

Q10. Gemini 지연·실패 시 전략
기다리지 않는 것이 기본값입니다. 상담 경로에서 웹 탐색을 뺐으므로(전제 ① 해소), 실패는 수집 파이프라인의 문제로 격리되고 사용자 응답 시간에 영향이 없습니다.
부분 결과는 제시하되 스냅샷 고정: 사용자에게 제시된 후보 세트는 세션 내에서 버전으로 고정하고, 백그라운드 보완으로 바뀐 내용은 제시 목록을 조용히 교체하지 않고 "N건의 변경/신규 후보가 있습니다" 알림으로 분리합니다. 사용자가 비교 중인 목록이 밑에서 바뀌는 것이 선택 방해의 주요 원인이므로 이것만은 막아야 합니다.
장기 실행이 꼭 필요한 작업(대량 상세 수집)은 폴링 기반 비동기 실행을 씁니다. OpenAI Responses API의 background 모드처럼 장시간 작업을 비동기로 돌리는 공식 경로가 존재합니다. 단, 이 모드에서 요청이 수락 후 실행되지 않고 큐에 멈추는 사례가 보고된 바 있으므로, 타임아웃 후 취소·재제출 로직은 필수입니다.
30초 제한 자체가 외부 플랫폼(GPT Sites)의 요청 한계라면, 동기 요청 내 완결이 불가능한 작업을 그 안에 두고 있다는 설계 신호로 읽어야 합니다.
