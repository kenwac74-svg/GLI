# GLI 점진적 검색·상담 방향 및 기술 검토

작성: 2026-10-30
담당: 현재 GPT 총괄 사업기획·PM — 방향 설정, 기술 조사, 구현안 선택과 결과 검토.
실행 담당: GLI 데모 개발 — 승인된 범위의 구현·실측.
상태: **개발팀 전달 제안. 공식 기능과 기존 증거의 조사 결과이며, 구현·신규 유료시험·배포 승인이 아니다.**

## 1. 사용자 의도와 이번 제안의 경계

사용자는 한 번에 모든 정보를 모아 긴 답을 내기보다, 첫 질문에 콤팩트하고 적절하게 답하고 남은 관심·정보 부족을 후속 질문으로 이어가도록 지시했다. 미리 예상한 질문에 맞춰 고객 입력을 다듬는 방식은 지양한다. 목적 밖의 질문에는 부드럽게 일반 AI 이용과 GLI의 역할을 안내한다. 이 관점의 검색 방향성과 기술 연구는 PM이 맡는다.

기존 마스터 §0.1, 최소자원 원칙, 단일 공통 검색, OpenRouter 재사용, 사람의 정보 확보 역할과 정합적이다. P-010의 단발성 답변 비교를 정상적인 대화 흐름의 관찰로 확장하되, 기존 원문·실패 증거는 수정하지 않는다. 다음의 구체적인 반환 형식·제안 개수·클릭 동작은 PM 제안이며 사용자 확정 정책으로 승격하지 않는다.

목표: **각 답변 자체가 유용하고, 다음 질문은 선택을 돕는다.** 반복 방문이나 클릭을 늘리려고 이미 답할 수 있는 핵심을 의도적으로 숨기지 않는다. 짧은 답이 정보 부족을 포장하는 수단이 되어서는 안 된다.

## 2. 조사로 확인한 사실

### 프로젝트에서 확인한 사실

- 기준 증거는 `fe009ffbb358c6195a05a320dd1adc4d87c0ec6d`의 P-010 다섯 유형 보고와 `scripts/p010-direct-search.mjs`다. 조회한 연구 브랜치 코드에도 모든 질문에 현재 웹검색을 요구하는 system 문구가 남아 있다. SOL 하나를 쓰지만 질문별 검색 필요성은 지시에서 구분하지 않았다.
- 다섯 답변의 첫 본문 수신은 9.244~17.859초, 완료는 15.445~44.084초였다. 쉬운 수익률 설명에도 검색이 기록됐다. 이를 모델만의 문제나 웹검색 하나만의 지연으로 단정하지 않는다.
- API의 후속 대상 연결은 성공 사례가 있다. 원화 예산 처리, 답변 분량, 검색 횟수 한도와 사용량 기록의 불일치는 남아 있다. GPT 웹의 정확한 속도 우열은 측정하지 못했다.

### 2026-10-30 OpenRouter 공식 문서에서 확인한 사실

| 확인한 기능 | 이 설계에 주는 의미 | 제한 |
|---|---|---|

| 스트리밍을 지원한다. [S4] | 완료를 기다리지 않고 실제 도착한 본문을 표시할 수 있다. | 검색 대기 자체를 제거하지 않는다. 서버 keep-alive와 '찾는 중'은 유용한 답변 수신시간이 아니다. |
| 지원 엔드포인트는 JSON Schema와 스트리밍을 함께 지원한다. [S5] | 본문과 후속 질문을 같은 응답에서 분리해 받을 후보 방식이다. | 모델명만으로 지원을 확정하지 않는다. 현재 계정/엔드포인트의 검색과 구조화 출력 조합은 이번에 실호출하지 않았다. |

위 내용은 공식 기능의 조사 결과이지 GLI에 이미 적용된 기능 목록이 아니다.

## 3. 선택하는 방향

**기존 OpenRouter + 현재 시험 SOL 하나 + 필요시 검색 + 짧고 유용한 답 + 선택형 후속 질문**을 다음 설계안으로 삼는다. 모델 교체, Astra 검수, 별도 질문분류 모델, 자동 다중 모델 평가, 새로운 API 계약을 먼저 추가하지 않는다.

고객 요청과 최근 대화·참조 대상을 같은 모델에 전달한다. 모델은 답변 과정에서 이번 질문에 현재 자료가 필요한지를 판단한다. 최신 매물·규정·가격처럼 실제 현재 근거가 필요한 경우 검색한다. 제공된 수치의 계산·기존 답변 풀이·가벼운 인사에는 불필요한 검색을 요구하지 않는다. 별도의 '분류 호출'을 먼저 실행하지 않는다.

빠른 첫 답을 위해 원래 요구를 제멋대로 축소하지 않는다. 예산 적합성을 묻는 질문에서 원화 비교는 핵심이므로, 이미 확보된 날짜 있는 환율정보를 이용하거나 필요한 자료를 조회한다. 더 많은 사진이나 선택 후보 확대는 후속으로 남길 수 있지만, 예산도 확인하지 않은 목록을 예산 적합 추천처럼 보여주지는 않는다. 모든 후보가 완전 실사될 때까지 답변을 금지하는 것도 아니다.

사용자가 상세 비교나 긴 설명을 명시하면 그 요구를 따른다. 무조건 3문단, 3개 후보, 하나의 표로 제한하지 않는다. 첫 단계의 목적은 '고객이 당장 알고 싶은 것에 답하기'이지 '항상 짧게 자르기'가 아니다.

## 4. 서비스 범위와 예상하지 못한 질문

단어별 차단표 대신 질문 목적과 앞선 맥락을 본다. 아래는 정적 템플릿 목록이 아니라 행동 원칙이다.

- 부동산·거주·관련 생활환경·투자판단에 연결되면 관련 범위에서 돕는다. 정치·의료·날씨라는 단어만으로 배제하지 않는다.
- 현재 맥락의 '두 번째', '거기', '관리비'를 이어받는다. 불명확한 대상은 짧게 확인하며, 없는 후보를 만들지 않는다.
- 인물 소개 등 명확히 목적 밖인 요청에는 긴 조사 없이 일반 AI 이용과 GLI가 도울 일을 짧게 안내한다. 현재 직책 같은 변동 사실을 검색 없이 덧붙이지 않는다. 인사에는 인사로 응답한다.
- 질문의 일부만 관련되면 관련 부분에 답하고 나머지 범위를 자연스럽게 알린다. 내국 DB 부족이나 조회 오류를 '서비스 범위 밖'으로 처리하지 않는다.
- 맥락이 애매할 때 무조건 이탈을 유도하지 않는다. 관련성이 의심되면 가능한 짧은 도움 또는 핵심 확인 하나를 선택한다.

이 판단은 같은 응답 모델이 한다. 프롬프트만으로 비용·보안·접근권한을 보장하지 않는다. 도구는 허용된 검색·조회만 제공하고 외부 자료의 지시는 실행 권한으로 취급하지 않는다.

## 5. 후속 질문과 반환 형식

### 질문 제안 원칙

방금 답변과 실제 미해결 부분에 근거해 **고객이 입력할 법한 명령**을 만든다. 예: '첫 번째 후보의 최근 임대 광고를 더 찾아줘', '두 후보의 생활환경을 비교해줘'. 예시 문구를 모든 답에 고정하지 않는다. 이미 답한 내용을 반복하거나 첫 질문의 필수 답을 일부러 뒤로 미루지 않는다.

대체로 0~3개 중 필요한 만큼이라는 안을 제안한다. 아무 제안 없이 끝내도 된다. '예산을 알려주세요'처럼 고객에게 질문하는 문장과 '예산 안에서 다른 후보도 찾아줘'처럼 고객이 다음에 보낼 명령을 구별한다. 앞선 지침의 '확인 질문 하나'는 모델이 사용자에게 묻는 요구의 수이며, 선택형 후속 명령 2~3개와 다른 개념이다.

GLI가 실제로 수행할 수 없는 '등기 안전 보증', '현장 확인 완료', '자동 연락' 등을 제안하지 않는다. 클릭하지 않은 후보 질문들을 미리 검색하거나 답을 생성하지 않는다.

### 최소 기술안

호환성이 확인되면 같은 생성 응답을 `answer_markdown`과 `followups` 목록으로 나누는 최소 JSON 형식을 사용한다. 본문 안의 문단·표 구성은 자유롭게 둔다. 출처는 제공자 annotations와 기존 증거 참조를 유지하고, 모델이 적었다는 이유만으로 확인 완료 표시를 붙이지 않는다. 전체 페이지 HTML 생성이나 별도 모델의 재요약은 하지 않는다.

스트림에서 본문 필드를 읽는 대로 표시하고, 후속 목록은 완결·검증된 뒤 활성화한다. JSON 전체가 끝날 때까지 본문을 숨기면 안 된다. 빈/불량 후속 목록은 생략하고 이미 유효하게 받은 본문을 폐기하지 않는다. 구조화 출력이 사전 검사에서 지원되지 않으면 이를 자동 모델 변경이나 반복 유료 재시도로 덮지 않는다. 본문 우선의 표시와 기존 프로토콜 재사용을 유지하고 실패를 보고한다.

시안의 옅은 제안은 '자동 실행되지 않은 입력 후보'로 표현한다. 첫 구현 제안은 누르면 입력창에 편집 가능한 문장을 넣고 사용자가 전송할 때 실행하는 방식이다. 키보드로도 접근할 수 있어야 하며 실제 disabled 버튼만 제공해 선택 불가능하게 만들지 않는다. 클릭 즉시 실행 방식은 별도 UX 선택으로 남긴다.

서버는 후속 요청에 원 답변 ID, 실제 참조 자산, 최신 사용자 수정 조건을 연결한다. 최근 대화와 후보 맥락은 세션 수준에서 유지하되 전체 대화의 영구 저장을 이번 제안에 포함하지 않는다. P-009 관리자 기록에는 실제 실행한 검색명령과 필요한 조건을 남긴다. 제안만 출력된 문구를 실제 고객 검색수요로 집계하지 않는다.

## 6. 다음 실험의 범위와 완료 기준

기존 P-010 원문·설정·결과는 기준으로 보존한다. 모델과 검색엔진을 동시에 바꾸지 않는다. 첫 비교는 '매번 검색·한 번에 상세 답변' 대신 위 공통 대응정책을 적용한 차이에 한정한다. 한 번에 전체 UI나 모든 수집기를 다시 만들지 않는다.

기존 다섯 유형을 답안 암기용으로 쓰지 않는다. 같은 고객 의도의 표현 변형, 서비스 밖 질문, 관련·무관 혼합, 대상이 애매한 후속, 주제 전환을 소수 추가해 일반적인 행동을 본다. 매회 동일 문장·동일 후보가 나오는지보다 핵심 조건 대응, 적절한 검색 사용, 정보의 성격 보존, 쉬운 다음 행동을 확인한다.

후속 한두 번까지 실제 흐름으로 확인하되, 대화가 길수록 성공이라고 보지 않는다. 첫 유용한 본문 시간과 요청 목적을 해결하기까지의 전체 시간·모델/검색 비용을 함께 기록한다. 짧은 첫 답으로 모든 일을 여러 번에 나눠 총비용만 늘어난 경우도 실패 후보로 본다. 이전 웹 속도는 미측정이므로 비교값을 새로 만들어 넣지 않는다.

검색 한도 불일치는 미해결이다. PM은 공식 계약과 증거의 차이를 계속 검토하고, 개발 담당은 승인된 로컬 범위에서 실제 요청·반환 usage를 계측한다. 이를 이유로 유료 호출을 무한 반복하거나 native/Exa 차이를 추정으로 확정하지 않는다. 정량 상한과 추가 유료 실행 범위는 실험 전에 명시한다.

산출물은 고객 답변과 실제 후속 동작, 관련 호출 기록, 실패와 한계다. 복잡한 자동채점기나 별도 분류 모델은 이번 범위가 아니다. 생산 코드 변경·운영 검색 교체·A/B 병합·배포는 이 조사 문서로 승인되지 않는다. Git 기록과 개발 세션 수신/실행을 구별한다.
