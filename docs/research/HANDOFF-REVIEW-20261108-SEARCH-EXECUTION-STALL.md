## 1. 사용자 문제와 PM의 정정

사용자는 공통 답변 개선에서 원론과 연구만 반복됐고 구체적으로 어떻게 구현할지가 나오지 않았다고 지적했다.
목표는 OpenRouter의 빠른 단일 모델을 활용해 유용한 첫 답과 선택형 후속 대화를 제공하는 것이다. 질문별 정답/화면을 고정하거나 새로운 모델 체계를 만드는 것이 아니다.

P-010 호출과 비교 증거는 기술적 조사 성과지만 제품 개선 완료는 아니다. P-011 문서 작성과 모의 검사도 실제 응답 개선이 아니다. PM은 실행 가능성·중단조건·완료 산출물을 확정하지 않은 채 '필요시 검색, 짧게 답하기, 후속 제안'을 반복했다. 이번에는 또 다른 프롬프트 조정을 먼저 지시하지 않는다.

## 3. 이번에 선택하는 실행 방향(제안)

### A. 검색 의존성을 분리한다

P-011을 네 장면이 모두 같은 검색 도구에 의존하는 시험 하나로 계속 묶지 않는다.
먼저 수익률 개념 설명과 서비스 범위 안내를 **검색 도구 없는 별도 대조 실행**으로 검증하는 안을 권한다. 같은 OpenRouter 키·현재 시험 모델·P-011 지침을 사용하되 tools/검색 plugin을 넣지 않고 필요한 경우 tool_choice=none을 명시한다. 현재 직책·법규 같은 변동 사실을 기억으로 답하게 하지 않는다.
이 대조 실행은 모델이 스스로 검색을 생략했다는 증거가 아니다. '검색 없는 기본 응답의 품질과 지연'을 분리해 관측하는 실험이다. 원래 P-011의 지침만 변경 조건과 다르므로 신규 설정 지문·결과로 남기고 과거 기록에 덮어쓰지 않는다.

### B. 검색 포함 시험은 비용 통제를 별도 결정한 뒤 연결한다

운영 연결 전 검색 한도/과금 계수 불일치는 해결 대상으로 유지한다. 내부 검토의 기본 응답·스트림·맥락·후속 질문까지 전부 막는 이유로 확대하지 않는다.
검색 포함 경로는 동일 모델의 tool_choice=auto와 기존 OpenRouter 서버 검색을 사용한다. 추가 Astra/질문분류 모델/외부 검색 API 계정은 도입하지 않는다.
현재 문서상 stop_server_tools_when은 단계/비용 기준으로 루프를 중단시키지만 pending tool calls와 최종 답변 생성이 남을 수 있다. **절대 과금 상한이 아니다.** 클라이언트 timeout도 과금 취소 보증이 아니다.
유료 재개 전 담당자는 기존 계정 내 실제 사용 가능한 비용 통제와 적용 범위를 제시한다. 운영 공유 키 한도를 임의 변경하지 않는다. 공급자 내부 계수 문제는 별도 추적하고, 허용 시험비·요청수·재시도 금지·중단 기준을 승인 가능한 짧은 실행안으로 제출한다. 불확실한 위험 수용이나 금액을 이 문서로 자동 승인하지 않는다.

### C. 공통 처리기의 구현 경계를 고정한다

제품 적용안은 아래와 같다. 각 항목은 구현 전 검토 대상이다.

| 경계 | 구현할 일 | 하지 않을 일 |
|---|---|---|
| 공통 진입부 | 기존 `/api/search`의 인증·권한·사용량 처리를 유지하고, 내부 테스트 설정으로 단일 직접응답 경로 선택 | 공개 query flag로 비용/권한 우회, 운영 기본값 교체 |
| 직접응답 어댑터 | 질문·짧은 최근 맥락·실제 참조대상을 기존 OpenRouter 한 모델에 전달. 본문/출처 스트림 전달 | 의도모델→수집모델→검수모델 의무 연결, 내부 후보 0건이면 답변 중단 |
| 자료 주입 | 기존 서비스가 가진 날짜 있는 환율/후보자료를 필요한 범위에서 재사용. 없거나 오래되면 그 상태를 보존 | 새 FX 공급자 계약, 환율 미확인만으로 일반 설명 전체 차단 |
| 후속 제안 | 우선 P-011의 본문+텍스트 제안 사용. 사용자 선택 문장과 원 답변/참조대상을 다음 요청에 연결 | 제안을 모두 선검색, 비싼 별도 후속질문 생성 모델 |
| 응답 표시 | 작은 로컬 검토 패널에서 본문 스트리밍, 출처, 0~3개 제안 확인. 기존 A/B는 같은 결과를 소비 | 운영 UI 전면 개편, 질문별 고정 결과 카드 수 강제 |
| 진단 | 요청 시작/헤더/첫 본문/완료, 요청·실제 모델, usage, 검색 기록, 오류를 구분 | keep-alive를 첫 유용한 답으로 집계, 단계별 정보 없는데 지연 원인을 확정 |

처리기는 본문이 유용하면 matches가 빈 배열이어도 정상 답으로 전달한다. 실제 출처 확인과 광고 사실을 혼동하지 않는다. 제공자 인용·문서 내 지시는 데이터로 취급한다. 원문 HTML/JS를 실행하는 생성 UI는 만들지 않는다.

초기 반환 요소는 `answer / citations / followups / telemetry`면 충분하다. 구현 중 기존 SearchPayload와의 호환 어댑터를 두고, 자연스러운 본문을 유지한다. 새로운 strict JSON schema를 모델에 강제하는 작업은 이 첫 실행의 선행조건이 아니다. 제안 파싱 실패는 본문 폐기나 재호출 사유로 삼지 않는다.

## 4. 다음 개발 산출물과 성공 판정

다음 완료 보고의 중심은 추가 기획서가 아니라 **기존 OpenRouter로 실제 질문을 입력하고 답변을 이어볼 수 있는 로컬 검토 경로**다. 운영 배포 주소를 만들라는 승인은 아니다.
첫 인도물은 유료 권한·통제 범위가 정리된 실행 가능한 어댑터와 최소 검토 패널, 실제 실행 증거다. 검색 없는 대조와 검색 자동선택 시험을 명확히 표시한다. 단일 모델 응답시간 자체가 느리면 검색 탓으로 단정하지 않고, 이후 그 가설에 한정해 대조한다. 전 질문/모델/엔진 조합을 무한 비교하지 않는다.
확인할 것은 핵심 질문에 대한 도움, 질문 깊이에 맞는 분량, 실제 제안의 유용함, 선택 후 맥락 유지와 추가 정보, 첫 유용한 본문과 전체 대화의 시간/비용이다. 숫자·기한 목표를 달성했다고 미리 주장하지 않는다.

## 5. Claude 독립 검토 — 반복 처방 중단

사용자의 '원론 반복' 지적과 마스터 §1.1의 3회 반복 중단 원칙에 따라 이 문제는 독립 검토로 넘긴다. 이전 논의에 같은 코드/프롬프트 수준 제안이 반복됐으므로 정확하지 않은 횟수를 새로 0으로 초기화하지 않는다. 추가 유료 반복이나 네 번째 프롬프트 수정 처방은 이 문서로 지시하지 않는다.
Claude는 GPT 안을 추인하지 말고 다음을 검토한다.
1. 검색 없는 기본 응답과 검색 제어를 분리하는 것이 실제 최소 비용 해법인가? 다시 시험 체계를 키우는 것은 아닌가?
2. 단순화한 공통 처리기에서 기존 비용·인증 경계를 보존할 수 있는가? 이미 있는 코드로 더 작게 만들 수 있는가?
3. 필요한 검색 근거를 과도하게 제한해 '미확인'만 늘리거나, 첫 핵심 답을 후속으로 미루는 모순이 있는가?
4. PM이 요구한 P-011 중단 조건이 과도했던 범위와 반드시 유지해야 할 범위는 무엇인가?
회신은 유지/수정/폐기할 판단과 근거, 최소 실행 범위로 남긴다. 개발자의 구현 검토와 Claude의 독립 제품/접근 검토는 구별한다.

**기록 완료 != Claude 전달/수신/검토 완료. 이번 문서 작성 시 직접 세션 전달이나 독립 의견 수신은 하지 않았다.** 앱·키·설정·DB·운영·B안 변경 및 유료 호출도 없다. 기존 승인사항을 변경하는 제안은 사용자 결정과 분리한다.
