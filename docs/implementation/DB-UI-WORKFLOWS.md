# DB 기반 UI 연결

## 2026-10-13 LOCAL 구현 정정

아래 초기 관심 연결 설명과 설계 대기 기록은 HIST-20261013-009로 갱신된다. 고객 UI → 인증 `/api/favorites` → `db/asset-favorites-repository.ts` → D1 `asset_favorite_refs`/`asset_references`가 현재 경로다. 정식/외부/승인 fixture 저장을 지원하며 기존 관계는 회원별 lazy 이관한다. 원문 삭제/거래 완료는 보관하고 해제는 본인 관계만 삭제한다. 비공개 정식 자산의 신규 사용자 등록은 거절한다. partial 상태는 실제 회원 브라우저/공개 QA 미완료 때문이며 외부 참조 미구현 때문이 아니다. 가격 이력 화면은 별도 Claude 담당이고 MY는 순서6에 유지한다.

## 승인 경계 (2026-10-12)

사용자는 화면의 미연결 기능 중 목업으로 구현 가능한 항목을 진행하되, 브라우저 저장을 DB 대용으로 사용하지 말고 추후 정식 DB 구현을 전제로 연결하도록 지시했다. 기존 D1과 계정 API를 우선 재사용한다. 공개 배포/권한 완화/실결제/새 디자인 승인은 아니다.

## GS-016 관심자산

- 고객 UI → `lib/favorite-client.ts` → `/api/favorites` → 회원 인증 → `db/user-workflows.ts` → D1 `favorites`.
- GET: 로그인 계정의 ACTIVE listing 관심 목록만 반환. 응답은 no-store. 가격 minor 단위, 통화, 침실 null/Studio 0, 면적을 보존한다.
- POST/DELETE: 기존 계정 소유권, Origin/JSON 검사, 중복 방지, 멤버십 한도 및 감사 이력을 유지한다. UI는 DB 성공 후 목록을 재조회한다. 실패를 저장 성공처럼 표시하지 않는다.
- 목록/샘플 상세/동적 상세의 저장·해제 및 관심자산 페이지를 연결한다. 기존 카드/하트 디자인을 재사용한다. 로컬스토리지에 관심 목록/계정/권한을 저장하지 않는다.
- 비로그인은 기존 로그인 경로를 사용한다. 공개 상담의 비로그인 허용을 관심자산 인증 해제로 확대하지 않는다.
- AWS 이전 시 API/자산 public ID/계정 소유권 계약을 유지하며 DB adapter를 교체한다. 클라이언트에 SQL이나 클라우드 접근키를 넣지 않는다.

## 남은 범위

### 2단계 보관 결정 (2026-10-13)

- 사용자 승인: 원문 삭제/거래 완료된 관심자산도 마지막 확보 정보를 보관하고 상태를 구분한다. 사용자의 관심 해제와 매물 정보 자체의 삭제는 별개이다.
- 검색에서 수집 대상으로 판단하여 실제 확보한 후보를 DB에 계속 보관한다. Top5 밖이거나 사용자가 관심 저장/열람하지 않아도 저장 대상이다. 브라우저/프로세스 메모리를 영속 저장의 대체로 쓰지 않는다.
- 보관 자료를 현재 거래 가능/검증 완료로 표시하지 않는다. 차단·조회 실패만으로 거래 완료/원문 삭제를 단정하지 않는다. 수집 시각과 원문 날짜는 구분한다.
- 최신 정보와 변경 이력을 함께 보관하는 방식은 사용자 승인(2026-10-13)으로 확정했다. 가격/설명/상태 변화 시 이전 값·변경 관측 시각을 남기며 내용이 같으면 확인 시각만 갱신한다. 원문 날짜/수집 시각 의미를 유지한다.
- 얇은 재수집에서 필드가 누락된 것을 사실상 삭제/변경으로 오인하여 기존 제원/설명/사진을 지우지 않는다. 정규화 내용 비교와 부분 갱신 계약을 구현 설계에서 정한다.
- 출처 간 중복은 동일성이 확실할 때만 묶고 출처별 정보/값/이력을 유지한다(2026-10-13 승인). 불확실하면 별개로 보관하고 유사 면적/동일 건물만으로 다른 호실을 합치지 않는다. 병합 전 관심 참조의 복원/안정 ID 매핑을 유지한다.
- 충돌하는 가격/상태 등은 병합으로 소거하거나 다른 출처의 확인 사실로 바꾸지 않는다. 같은 출처의 최신본과 출처 간 비교를 구분한다.
- 고객 공개 범위 승인(2026-10-13): 최신 정보와 가격 변경 이력만 제공하고 설명/사진/수집 기록 등 전체 변경 이력은 관리용으로 보관한다. 새 표시 디자인은 Claude Design에 전달한다.
- 기술 설계 제안과 검증 경계는 DISCOVERY-RETENTION-DESIGN.md에 기록했다. 기술 설계 자체는 검토 대기이며 구현 계획과 별도이다.
- 삭제/보관 상태 필드, 확실한 동일성의 구체 증거 기준 및 API 조회 계약은 후속 설계에서 정한다. 이번 결정만으로 기존 데이터 삭제/실서비스 DB 쓰기/수집 확대/배포를 시작하지 않는다.

- 현재 `favorites.listing_id`는 `listings` 외래키이다. `discovered_assets` 외부 후보/정적 프로젝트가 정식 listing으로 등록되지 않았다면 기존 API는 저장을 거절한다. 프론트 캐시나 임의 listing 삽입으로 성공을 가장하지 않는다.
- 차후 정식 listing과 discovered 후보의 안정 ID 참조를 함께 지원하는 저장 모델, 삭제·게시 중단·중복 병합 이후 참조 정책을 설계해야 한다. GS-016은 partial로 유지한다.
- 실제 로그인 계정의 브라우저 저장/새로고침/다른 기기 일관성과 공개 환경 검수는 별도이다. 현재 증거는 로컬 비로그인 UI와 격리된 SQLite 기반 built-worker 계정 API 시험이다.
- 보기 모드, BASIC 샘플 열람, MY/예약/커뮤니티 등의 미연결 항목은 이번 관심자산 연결로 완료했다고 간주하지 않는다. 실결제/권한 원장은 목업 표시 상태와 분리한다.
