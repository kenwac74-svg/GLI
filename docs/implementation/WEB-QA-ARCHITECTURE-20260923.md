# GLI 웹 QA: 서버 구조·토큰 비용·개발 인계

검수일: 2026-09-23. 사용자 요청으로 Codex가 검수하고, 독립 웹 QA 보조 에이전트 1명이 AI 유료 호출 경로를 별도로 점검했다. 실제 외부 인력 고용이나 인증 심사가 아니다.

## 범위와 판정

후속 구현 기록: 사용자 개선 승인 및 P38(전체 300/계정 100회) 이후 Q1/Q2/Q4/Q5/Q6의 1차 보호를 구현했다. [AI-OPERATING-GUARD.md](AI-OPERATING-GUARD.md)와 HIST-20260923-014를 참조한다. 아래 발견/행 번호/미구현 표현은 최초 QA 당시 증거로 보존한다. Q3 영속 후보, Q7 최종 시안 통합, 분산 중복 방지/공개 무료 신원 등은 계속 미완료다.

대상은 현재 작업 트리의 React/서버 소스와 마지막 수령한 GLI-052-R 디자인 패키지다. 두 소스를 이미 통합된 것으로 취급하지 않는다. 새 디자인·문구·공개 배포 승인은 별개다.

| 질문 | 판정 | 의미 |
|---|---|---|
| 서버에 빌드할 수 있는가? | 현재 Cloudflare 대상 빌드 통과, 실서비스/AWS는 부분 준비 | 실제 별도 사본에서 빌드·207개 테스트 성공. AWS 바로 배포 가능 또는 운영 완성을 뜻하지 않음 |
| 불필요한 토큰 낭비를 막는가? | 공개 운영 기준 미통과 | 유료 단계 전체를 포괄하는 한도/시도 원장이 없고 중복·취소·대화 길이 계약에 보완 필요 |
| 소스에서 정책·이력을 이해하고 기획서를 만들 수 있는가? | 전체 저장소 기준 조건부 가능 | 정책/현황/계약/백로그/이력/코드 연결이 존재. HTML/생성 코드 또는 마지막 디자인 ZIP만으로는 부족 |

심각도는 실서비스에 적용했을 때의 영향 기준이다. 알려진 데모 한계를 새 회귀 버그로 표현하지 않는다. 아래 수정 제안은 미구현이며 이번 검수에서 제품 소스는 변경하지 않았다.

## 주요 발견

### Q1 · P1 · Gemini 유료 작업이 상담 이용권 검사와 분리됨

- 근거: `app/api/search/route.ts:106`의 이전 후보 번역은 회원 조회보다 먼저 실행된다. 157~161행의 Gemini discovery 조건에는 국가·설정·일치 후보 수만 있으며 상담 이용 가능 여부가 없다. 178행의 결과 번역도 별도 실행이다.
- 영향: 해당 서버 기능과 키가 켜져 있고 캐시가 비어 있으면, 비로그인 또는 상담 한도 소진 요청도 유료 탐색/번역을 유발할 수 있다. 공개 배포 설정 자체는 이번에 확인하지 않았다.
- 무료 체험 제공은 사용자 승인 방향이므로 금지 대상이 아니다. 문제는 무료/회원/운영자 전체 사용량을 제한하는 공통 비용 경계가 없다는 점이다.
- 제안: 모든 유료 단계의 시작 전에 서버 측 작업 예산을 예약하고, 익명/회원별 요청 빈도와 운영자 총비용 상한을 적용한다. 비용 상한 숫자는 별도 결정한다. 캐시 hit는 불필요하게 과금 횟수로 세지 않는다.

### Q2 · P1 · 상담 횟수 반환과 실제 발생 비용이 분리되어 기록되지 않음

- 근거: `app/api/search/route.ts:203`은 최종 advisor가 rules면 상담 사용 횟수를 반환한다. 의도 해석에서 이미 비용이 발생했거나, `lib/ai-search.ts:335`처럼 유료 생성 후 결과 검증에 실패한 경우도 해당한다. 내부 진단/사용량은 공개 응답에서 제거되지만 별도 영속 비용 원장에 남기는 호출은 없다.
- 영향: 반복 실패 또는 확인 질문에 유료 의도 해석이 선행되면 고객 잔여 횟수는 복구되면서 운영자의 비용은 반복 발생할 수 있다. 이것은 고객에게 실패를 과금해야 한다는 결론이 아니다.
- 제안: 고객 상담 횟수와 운영자 실제 시도·토큰·비용 원장을 분리한다. 단계별 usage, 실패 이유, request ID와 실패 연속 횟수를 기록하고 과도한 실패 시 차단한다. 이미 발생한 모델 비용이 환불됐다고 표시하지 않는다.

### Q3 · P1 · 공개 검색 후보가 서버 인스턴스 간 영속 데이터가 아님

- 근거: `lib/cambodia-live-discovery.ts:32` 이후 Map/no-op 저장소 경계가 주석으로 명시된다. `lib/gemini-discovery.ts:64`도 결과를 process-local Map에 저장한다. `lib/assets-data.ts:51`의 상세 조회는 이 Map을 먼저 읽는다.
- 영향: 검색과 상세/후속 질문이 다른 Worker 인스턴스에 배정되거나 프로세스가 재시작되면, 방금 본 외부 자산을 재조회하지 못할 수 있다. 한 서버에서 빌드·단위 테스트가 성공해도 해결되지 않는다.
- 기존 상태: GS-004와 AWS-MIGRATION에 이미 미완료로 정확히 기록되어 있다. 별도 승인 ingestion의 D1/R2 저장 기능과 공개 discovery 연결을 혼동하지 않는다.
- 제안: 공개 가능한 원문·정규화 자산·출처를 durable repository에 저장하고 ID로 조회한다. 재시작/다중 인스턴스 계약 시험을 출시 조건에 포함한다.

### Q4 · P2 · 빌드 검증 명령에 타입 검사가 빠져 있음

- 근거: `package.json:16`의 test는 build 후 Node tests, 17행의 check는 lint/DB/test다. TypeScript 검사는 실행하지 않는다.
- 재현: 별도 사본에서 `npm run check`는 성공했지만 `tsc --noEmit --incremental false --pretty false`는 실패했다. `.ts` import 설정, Cloudflare 타입 누락 외에도 `app/api/admin/ingestion/import/route.ts:68`의 인자 수, `app/api/assets/route.ts:21`의 거래유형, `ingestion/source-policy.ts:202`의 connector 계약 등 오류가 있다.
- 영향: 번들 생성 성공만으로 인터페이스 정합성을 보장하지 못한다. 오류가 모두 실제 런타임 장애라는 뜻은 아니며 기존 오류도 포함한다.
- 제안: runtime 타입/tsconfig와 실제 계약 오류를 구분해 수정한 다음 typecheck를 CI 필수 검사로 추가한다. 전체 오류를 무시하는 방식은 권고하지 않는다.

### Q5 · P2 · 동시 중복 탐색과 이탈 요청의 비용을 줄일 장치가 부족함

- 근거: `lib/gemini-discovery.ts:146`은 완료 캐시만 확인하고 238행에서 완료 후 저장한다. 진행 중 Promise 공유와 실패 cooldown이 없다. 보조 QA의 모의 시험에서 동일 요청 3개를 동시에 보내면 공급사 호출 3개, 연속 HTTP 실패 2번은 호출 2개가 발생했다.
- `app/components/claude-design-shell.tsx:595`의 fetch에 취소 signal이 없고 서버도 request.signal을 유료 단계에 전달하지 않는다. 의도/상담은 각자 타임아웃만 사용한다. 화면 이탈 후 계속 실행되는지는 호스팅 동작에 따라 다르나 앱 수준의 다음 단계 중단은 보장하지 않는다.
- 제안: 의미가 같은 요청의 in-flight 공유, 짧은 실패 cooldown, 서버 request idempotency, 단계 시작 전 취소 확인을 추가한다. 사용자 문장을 의미 손실이 생기도록 과도하게 정규화하지 않는다. 이미 발생한 비용을 취소가 되돌리는 것은 아니다.
- 기존 보호: 완료 discovery 캐시는 10분이고, 번역 경로에는 이미 hash/R2 재사용·동시 요청 공유·실패 cooldown이 있다. 번역 보호를 탐색에도 재사용할 수 있다.

### Q6 · P2 · 긴 정상 답변이 다음 질문을 400 오류로 만들 수 있음

- 근거: `lib/ai-search.ts:653`의 상담 응답 스키마에는 답변 글자 수 상한이 없다. `app/components/claude-design-shell.tsx:591`은 표시한 답변을 그대로 최근 8턴에 넣고, `app/api/search/route.ts:286`은 한 턴 1,200자를 초과하면 거부한다. 화면의 answer와 clarification을 합친 값도 대상이다.
- 재현: 보조 QA의 모의 provider 응답에서 1,201자 답변이 정상 상담 결과로 받아들여짐을 확인했다. 그 길이는 위 다음 요청 검증과 충돌한다.
- 영향: 심화 상담 후 다음 질문이 실패할 수 있다. 400 검증은 유료 호출 전에 실행되므로 이것 자체를 반복 과금 루프로 단정하지 않는다.
- 제안: 화면 원문을 자르지 않고 모델에 재전송하는 대화 문맥을 별도로 제한한다. 구조화 조건·선택 자산 ID를 보존하고 초과 문맥 처리 방식을 명시한다. 요약을 위해 무조건 별도 AI 호출을 추가하지 않는다.

### Q7 · P2 · 최종 디자인 ZIP은 서버 앱 또는 현행 API 직결 납품물이 아님

- 근거: ZIP은 text/x-dc HTML/fixture/문서/이미지 9개이며 support.js·참조 이미지·서버 코드·package.json은 없다. 의도된 소형 디자인 인계 구성으로 수령은 정상이다.
- HANDOFF의 "fallbackRespond 한 곳을 API 호출로 바꾸면 된다"는 설명만으로 통합하면 안 된다. 수령 HTML `ingest`(3135행)는 `res.mode`, `res.reply`, 최상위 referencedAssetIds/missingAssetIds 및 `a{i}` ID를 사용한다. 실제 `app/api/search/route.ts:230` 응답은 answer와 중첩 consultation, 실제 공개 asset ID다.
- 제안: answer→reply, consultation.mode→mode, 참조 ID/누락 ID, resultSet/citations를 연결하는 타입 있는 adapter와 계약 시험이 필요하다. conditions/reasons는 기존 서버 계약에서 매핑하고 options는 미승인 예제를 실제 정책으로 이식하지 않는다. support.js/fallback rank를 서버 제품 로직으로 옮기지 않는다.
- 현재 Cloudflare 앱이 별도로 빌드되므로 전체 프로젝트가 빌드 불가능하다는 뜻은 아니다. 최신 시안 통합 승인이 필요하다는 경계다.

### Q8 · P2 · 정책과 이력은 있으나 최신 상태를 한 번에 인계하는 색인이 보완되어야 함

- 긍정: AGENTS와 implementation/README는 읽는 순서, 승인 우선순위, 이력 갱신, 제품/데모 구분을 명시한다. DECISIONS P35/P36, HISTORY, API-CONTRACTS, COUNTRY-SOURCES, AWS-MIGRATION, registry의 현재/목표/다음/근거/완료 조건이 있다. 코드에도 `GLI-SPEC: GS-...`와 뉴스 CMS·파트너 fixture·Map 저장 한계 주석이 있다.
- 한계: `registry.json:44`의 GS-001 요약은 초기 A1/A4 상태를 중심으로 되어 있어 최신 P35/최종 패키지 인계는 DECISIONS와 HISTORY 및 GLI-052 검수 보고를 더 읽어야 한다. 디자인 패키지는 work 검수 영역이며 프로젝트 소스 전체에 자동 포함되는 납품물이 아니다.
- 한계: OpenAPI는 검색/자산 목록 부분 명세이며 나머지 46개 route의 모든 오류/권한/입출력 계약이 완료된 것은 아니다. 이 부분 명세라는 사실 자체는 문서에 정확히 명시돼 있다.
- 제안: 통합 시 적용 기준 파일·해시·승인 문구·미승인 항목·API adapter 매핑을 한 인계 색인에 연결하고, GS-001 요약/검증 이력을 함께 최신화한다. 주요 정책 주석에는 정책 ID를 연결하되 정책 전문을 여러 소스에 복제하지 않는다. 문서 검사는 링크/ID 정합성 검사이며 의미 충돌을 자동으로 모두 찾는 검사가 아니다.

## 토큰 낭비로 단정하지 않은 것

- Astra의 의도 해석과 최종 상담은 서로 다른 승인된 역할이다. 매 질문 2회라는 이유만으로 한 호출을 제거하거나 품질 검증 없이 저가 모델로 대체하지 않는다.
- Fable 자동 단계/자동 공급사 fallback/무한 agent loop는 없다. P36 제외 방침을 유지한다.
- 최근 8턴, 후보 18개, 의도 4,096/상담 8,192/탐색 5,000/번역 8,192의 출력 상한이 존재한다. 상한은 실제 소비량이 아니다. 이번에 실결제 토큰 또는 절감률을 측정하지 않았다.
- review는 기존 후보 검토에서 재크롤링을 생략한다. 숫자 계산·Trust 판단·필터는 가능한 서버 결정 로직으로 유지한다.

개발 작업의 문맥 낭비도 구별해야 한다. `app/generated/claude-static.ts`는 약 2.61MB이며 여러 페이지/자산/권한 상태의 반복 HTML을 포함한다. 이를 매 작업의 입력으로 전부 읽는 것은 비효율적이다. 원본 약 288KB, 생성기, 해당 기능 파일, registry 근거부터 범위를 좁혀 읽고 생성 파일은 필요한 부분만 검사하는 것이 적합하다. 이 크기를 서비스 LLM 토큰 과금과 동일시하지 않는다. 이번 번들에는 500kB 초과 chunk 경고도 있었지만 UI를 임의 재작성하는 근거로 사용하지 않는다.

## 기획서 생성 가능 범위

**전체 저장소와 문서를 함께 제공하면 기획서 초안 생성이 가능하다.** 화면 코드만 보고 미구현 기능이나 승인 정책을 역추정하게 해서는 안 된다.

| 기획서 항목 | 1차 근거 |
|---|---|
| 제품 원칙·권한·가격·승인 경계 | DECISIONS, PRODUCT-DATA, 관련 정책 모듈 |
| 구현/데모/계획 및 국가별 연결 상태 | CURRENT-STATE, registry, COUNTRY-SOURCES |
| 화면·API·데이터·운영자 업무 | ROUTES, API-CONTRACTS/openapi, ADMIN, DB schema |
| 변경 이유·검증·미완료 사항 | HISTORY, 기능별 GLI 작업지시/검수 보고 |
| AWS 전환·출시 수용 기준 | AWS-MIGRATION, ACCEPTANCE, GS-025/032 |

기획서 생성자는 확정 정책/현재 동작/미구현 목표/새 제안을 분리해야 한다. 코드에 임시 처리가 있다는 이유로 그것을 사업 정책으로 확정하지 않는다. 최종 기획서의 미결정 수치와 새 문구는 사용자 승인을 받아야 한다.

## 이번 검증 증거
